## What was done

Implemented `extract_inject_markers` — the utility that scans content for all GSD_MODIFIER marker regions and returns them as a `dict[str, MarkerRegion]`. Refactored Slice 2's `find_marker` to use it internally while preserving apply-time tolerance via a single try/except. The strict-vs-tolerant split is principled:

- **`extract_inject_markers`** (new, public): strict — raises `MarkerExtractionError` on any structural anomaly. Used directly by Phase 2 Slice 4's `verify_inject_state` so verify-time surfaces corruption as a hard failure.
- **`find_marker`** (refactored): tolerant — catches `MarkerExtractionError` and returns None. Used by Slice 2's per-op apply functions so apply can still produce output when on-disk state is corrupt; the next verify run catches the corruption.

## Observations

- **Strict-vs-tolerant split is the load-bearing design choice**: apply-time tolerance lets the engine produce output even when on-disk state is malformed, but tolerance is honest only because verify-time is strict and will surface corruption next run. The two functions (`find_marker` for apply; `extract_inject_markers` for verify) make this calibration explicit at the API level.
- **Refactor preserves the apply-time signature contract**: Slice 2's per-op apply functions still call `find_marker(content, key)` with the same return type. The internal implementation changed (single-key scan → full extract + lookup), but the cases the Slice 2 apply tests exercise (clean content with one key per content) behave identically. The behavioral divergence is in the malformed-state branches the apply tests don't exercise.
- **Reviewer caught a docstring honesty gap**: the originally-written `find_marker` docstring claimed apply could "write a corrected file" when corrupt input was present, but apply is additive not corrective in the nested-but-closed / duplicate-key cases. The polish landed in-slice corrects the framing. This is a doctrine note for future modules: docstrings should describe what the code DOES, not what an idealized version of the code would do.
- **Failure-mode taxonomy is exhaustive for the structural anomalies**: nested / unbalanced_start / unbalanced_end / mismatched_end / duplicate_key cover all the structural states `extract_inject_markers` can detect. Empty-key and case-mismatched marker lines are silently treated as not-markers (would lead to unbalanced_start downstream) — accepted as low-likelihood per reviewer.
- **Slice 5 forward-looking test**: add a regression test asserting `find_marker(content, "A")` returns None on nested-but-fully-bracketed and duplicate-key structures for "A" — pins the behavioral divergence from old `find_marker`.
