### Per-kind verify semantics (codified in tests)

- **section_insert_after**: marker exists AND positioned after `</tag>` anchor line
- **section_replace**: marker exists (body content NOT asserted per ADR §8 V1)
- **step_remove**: marker exists with `<!-- GSD_MODIFIER:step_removed name:NAME -->` sentinel AND original `<step name="NAME">` block absent from non-marker regions
- **step_insert_after**: marker exists AND positioned after the anchor step's `</step>` line
- **include_add**: marker exists AND body contains expected line AND marker is positioned inside `<tag>...</tag>` body
- **include_remove**: marker is ABSENT (inverse post-state per ADR §3)
- **block_replace**: marker exists AND positioned between start_anchor and end_anchor (handles degenerate same-anchor)

## Observations

- **Strict-vs-tolerant split delivers in practice**: verify-time uses `extract_inject_markers` directly (per Slice 3's design intent); MarkerExtractionError surfaces as `VerifyResult.extraction_error`. Operator sees structural corruption named (nested / unbalanced / mismatched / duplicate-key) at verify-time, even when apply-time silently produced a fresh marker block to add to the corruption.
- **Per-kind verify mirrors per-kind apply effects**: each verify function asks "did this kind's apply effect actually land in materialized content?" without comparing source-file content (V2 territory). The asymmetry between section_replace (marker-presence-only) and step_remove (marker-sentinel + step-block-absent) reflects the different shapes of "did the op land": for section_replace the visible side is the marker (body content is the materialization step's concern); for step_remove the visible side is the step's absence + the sentinel marker (both must hold for the op to be considered landed).
- **VerifyResult is operator-triage-shaped**: marker_key + status + detail + op_index per verification; combined into "{target_path}: #{op_index} {kind} {marker_key}: {status}" for hard_failures. Operator can immediately identify the failing target, the failing op, and the failure category.
- **Materialization-report integration is backward-compatible**: the new `inject_verifications` / `inject_failures` / summary counts add fields to the report dict but don't modify existing fields. The 10 portable_gsd_contract tests all still pass; v3 paths unchanged.
- **OperationVerification.region delivers Slice 2 reviewer note (c)**: the optional MarkerRegion field on the verify-time record (NOT the apply-time OperationRecord) is the right placement — apply records what changed, verify records what was found.
