## Interventions Considered And Rejected

Each considered intervention names the upside, the regret analysis that rejected it, and a later signal that would justify reopening it. All are scoped against the same operator-bandwidth model as the switch triggers.

### 1. Full omnibus remap (replace Checkpoint 5 A1-A4 outputs with one new canonical topology)

- upside: produces a single clean authoritative map the rerun can lean on without reconciling four A-lane inventories; kills the partial-ledger and category-mismatch defects in one move.
- rationale considered: the readiness map as currently split is genuinely uneven and the bridge audit's warrant structure depends on topology grounding that is partly under-evidenced.
- regret analysis: omnibus remap is the same move the first readiness attempt implicitly rejected; doing it now would re-import the closure-biased incentive to treat the new map as settled truth; it would also lock in category choices before runtime probes have validated them. The pass-through cost is low (readers consult four files rather than one); the foreclosure cost is high (one authoritative topology under operator bandwidth is likely to freeze in the wrong shape for a rerun).
- later signal to reopen: two or more Wave-1 lanes converge on the same categorical re-classification, or an execute-and-learn pass shows the four-lane split is actively misleading.
- status: rejected; remains reopen-eligible only under signal trigger `#8` in the switch register.

### 2. Pre-Wave-1 harness-code-first intervention (`Proposal F` immediately, on the stale `.toml` agents)

- upside: closes the single most live runtime defect before the main wave opens, preventing the rerun from inheriting stale worker doctrine; provides a concrete, bounded repo-local target that fits the operator-bandwidth model.
- rationale considered: Checkpoint 4's strongest criticism was runtime-authoritative worker drift; live evidence on `2026-04-19` confirms it is still at `13/31`; the fix is mechanical.
- regret analysis: three problems. First, the stale-doctrine count is symptomatic; patching `.toml` files without fixing the overlay and installer would re-break on next install. Second, doing `F` now widens current Wave-1 scope before Wave-1 has produced its own mapping evidence, which is exactly what the charter warns against (`if a recommendation argues against a stronger intervention because it feels too large, it must say what execution model made it seem too large` — but the converse also holds). Third, executing a harness-code pass without a Wave-1-informed prioritization risks choosing the loudest drift instead of the most leveraged one; the helper-CLI plane and the materialization chain may actually matter more for a rerun than the `.toml` roster.
- later signal to reopen: a launch-truth capture (switch trigger `#1`) confirms a spawned planner inherited `CLAUDE.md` doctrine, or Wave-1 Lane 04 converges on runtime-authority as the dominant defect.
- status: rejected as a pre-Wave-1 move; promoted to switch trigger `#1` inside or after Wave-1.

### 3. Pre-Wave-1 comparative mapping lane (`Proposal C` applied before any rerun-design synthesis)

- upside: the present lane's findings would be stronger if a dedicated drift-probe lane ran first, probing runtime-vs-overlay, runtime-vs-upstream-docs, and runtime-vs-readiness-topology systematically rather than in a mapping-adequacy lane; C done well produces the intervention-ready map the charter asks about.
- rationale considered: bridge-audit lane-02 explicitly deferred this work to a `possible later lane`; no lane since has closed it; this present lane has to do partial drift probing on the side rather than as first-class evidence.
- regret analysis: C as a pre-Wave-1 gate would delay all four Wave-1 lanes for probably 2-3 weeks of operator bandwidth; it would also risk over-explaining every failure as a mapping failure (the charter's named risk in `Proposal C`'s description); and the existing Wave-1 structure is already capable of absorbing a bounded drift probe inside the Operator / Orchestration lane without needing a separate prior pass.
- later signal to reopen: Wave-1 produces runtime-drift findings that cannot be cleanly incorporated into the existing four-axis comparison without ontology reconciliation; in that case C becomes the prerequisite for Wave-1 synthesis rather than a replacement for Wave-1.
- status: rejected as pre-Wave-1 gating; promoted to a bounded expansion inside `Proposal B-extended` if Wave-1 evidence requires it.

### 4. Immediate launch-truth-as-machinery upgrade

- upside: would close the single most under-owned seam (effective launch settings) without needing a full harness rewrite; one concrete intervention that the map has been asking for since Checkpoint 4.
- rationale considered: the current launch-truth posture is honest but protocol-heavy; every doctrine-sensitive spawn depends on operator discipline to run `capture_launch_truth.py`; this is a single weak point the mapping keeps flagging without closing.
- regret analysis: two problems. First, it is tempting precisely because it is small, which means it can absorb attention that should go to the larger mapping question; `fix the thing you can fix` is exactly the closure bias the charter warns against. Second, launch-truth as machinery needs to interact with Codex subagent behavior that Codex docs describe as still-evolving (parent session overrides, feature maturity), so a repo-local machinery-first answer may be locally optimal but globally brittle.
- later signal to reopen: switch trigger `#4` fires, or a rerun relies on launch-truth evidence for a doctrine-sensitive audit and the operator notices capture drift.
- status: rejected as immediate move; staged behind switch trigger `#4`.

### 5. Docs-refresh backport into the repo (bring upstream lanes 12-15 gains into the repo's `.codex/` runtime)

- upside: the upstream docs-refresh work is genuinely high-quality (INVENTORY.md + 5 parity tests is the single strongest structural improvement in any of the artifact families); backporting it would tighten the repo's source-of-truth layer for agents/commands/workflows/references/modules/hooks.

- later signal to reopen: the repo grows a public-facing GSD-as-dependency posture (it currently does not), or the upstream refresh adds runtime-affecting features (not just doc truth) that a reinstall would pull in.
