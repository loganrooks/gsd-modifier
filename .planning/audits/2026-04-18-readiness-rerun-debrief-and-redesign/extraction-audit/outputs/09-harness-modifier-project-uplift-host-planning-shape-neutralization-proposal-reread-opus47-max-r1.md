## What Still Needs Sharpening

- The proposal names one carrier (`state_section.json`) plus one writer module plus a "typed phase-layout anchor" without committing on whether the phase-layout knowledge is a sibling key inside `state_section.json` or a distinct carrier. The two surfaces have different consumers: `state_section.json` is read by the writer module that rewrites `.planning/STATE.md`; the phase-layout grammar is read by `phase_boundary_signal`, `count_phase_files`, `latest_phase_context_path`, and `phase_sort_key` in the analysis path, with no dependency on STATE.md rewriting at all. Collapsing both into one carrier couples two independent extraction axes into one schema and one loader; splitting them intensifies the carry pattern the first two tranches set, where each typed carrier owns one axis (output policy, carrier catalog, vocabulary, seed contract, observation, declaration).
- The proposal is underspecified on how `state_heading` relates to the new carrier. `state_heading` already lives inside `output_policy.json` as `"## Project Uplift"`. The new carrier should reference the output-policy-owned heading rather than re-declare the string, otherwise two typed carriers quietly co-own the same token and the next drift of the heading only moves one of them. The sharper move is to keep `state_heading` owned by `output_policy.json`, let the state-section carrier carry sibling-marker names (`## Deferred Items`, `## Session Continuity`), the ordered label tuple, and the `.planning/STATE.md` path anchor, and let the writer module read both carriers at construction time.
- The proposal does not say whether the ordered label tuple inside the state-section carrier is a list of labels or a list of `(label, field_selector)` pairs. The first keeps data narrow and leaves field-selection dispatch helper-side in the writer module; the second pulls analysis-dict field names into the carrier schema and starts carrying rendering logic as data. Keeping the carrier as an ordered tuple of labels plus a separately-typed selector vocabulary, and keeping the dispatch from selector to analysis-dict field in `state_writer.py` code, preserves the same "typed data / helper logic" line the first two tranches drew.
- The proposal does not split the writer module's own internal surface. `state_section_text` renders the section body from analysis fields; `update_state_section` owns the marker-based rewrite of `.planning/STATE.md`. Both need to move, but they are different parity surfaces — a render-only fixture test covers the body bytes cheaply, while a rewrite test needs a fixture STATE.md. The writer module should expose a render entry and an update entry as separate callables so the tranche's parity test frontier can address them separately.
- The proposal's test frontier is implied rather than named. Tranche `157` landed a focused frontier in `tooling/codex/tests/test_project_uplift.py` covering loader shape, canonical section ordering, absent-additive stability, doctrine-reference-hash stability, carrier-fingerprint stability, and recommendation plus drift-reason equivalence across a no-op reorder. The planning-shape slice needs its own named additions: rendered state-section bytes unchanged on a representative analysis fixture; emitted uplift manifest fields unchanged on the same fixture; `latest_phase_context_path` and `count_phase_files` equivalence across a phase-layout-carrier read rather than embedded literals; `phase_sort_key` equivalence across the same carrier. Lane `08` named this frontier explicitly and the proposal should inherit it rather than leave it implicit.
- The proposal's governance-carry list does not yet name the `HARNESS-IMPROVEMENT-REGISTER.md` refresh or the sibling propagation-audit entry. Tranche `154` propagated through `57-harness-modifier-project-uplift-neutralization-change-triggered-refresh.md` and tranche `157` propagated through its own refresh entry. The third tranche should inherit that same propagation pattern explicitly rather than fold it into the generic carry list.
- The proposal does not name whether the held-later family artifact-home (`tooling/codex/UPLIFT-HELD-LATER.md`) is touched by this tranche. Lane `08` held that artifact-home question as a sibling decision to track once the planning-shape tranche picked up artifact-home posture; the proposal should say explicitly that this tranche does not move that file, so the later sibling decision stays visible.

## Recommended Planning-Shape Boundary

- Carrier split along the two consumer axes rather than one schema:
  - `harness_modifier/uplift/state_section.json` (+ `state_section.py` loader): owns `schema_version`, the `.planning/STATE.md` relative path, the ordered label tuple for the state-section body, a typed selector vocabulary the writer dispatches on, and the sibling-marker names (`## Deferred Items`, `## Session Continuity`) used by the insert algorithm. It references `output_policy.state_heading` rather than re-owning the heading string.
  - `harness_modifier/uplift/phase_layout.json` (+ `phase_layout.py` loader): owns `schema_version`, the `.planning/phases` root relative path, the phase-directory prefix grammar (separator `-`, dot-separated numeric-or-string phase key), and the discovery globs (`*/*-CONTEXT.md`, `*/*-PLAN.md`, `*/*-SUMMARY.md`). Consumers are the analysis path (`phase_boundary_signal`, `count_phase_files`, `latest_phase_context_path`, `phase_sort_key`), not the STATE.md writer.
- Writer module `harness_modifier/uplift/state_writer.py`: reads `state_section` and `output_policy` at call time, exposes at least `render_state_section(analysis, state_section_policy, output_policy)` returning body bytes and `update_state_section(repo_root, analysis, state_section_policy, output_policy)` performing the anchor-match / sibling-marker / trailing-append rewrite. `project_uplift.py` imports both and no longer edits `.planning/STATE.md` directly; the helper keeps classification and rendering code but calls through the writer for the section rewrite.
- Analysis-path rewire: `count_phase_files`, `latest_phase_context_path`, `phase_sort_key`, and the phase-root resolution inside `phase_boundary_signal` read `phase_layout.json` through its loader at analysis entry, matching the existing pattern where the helper reads typed policy data at entry rather than threading constants through every call.
- Test frontier named on the tranche rather than left implicit:
  - rendered state-section bytes unchanged on a representative analysis fixture;
  - emitted uplift manifest fields unchanged on the same fixture;
  - `update_state_section` output bytes unchanged across anchor-match, sibling-marker-insert, and trailing-append paths on three small STATE.md fixtures;
  - `latest_phase_context_path`, `count_phase_files`, and `phase_sort_key` equivalence after the phase-layout read replaces embedded literals, including a no-op reorder of phase-layout carrier keys where the carrier's declared ordering makes ordering a safe test surface.
- Propagation carry explicitly through `harness_modifier/overlay/helpers/AUTHORITY-MAP.md`, `harness_modifier/overlay/ROSTER.md`, `.planning/HARNESS-IMPROVEMENT-REGISTER.md`, `extraction-audit/README.md` (tranche count), `CURRENT-STATE.md`, `STATUS.md`, and a new propagation-audit entry modeled on `57` and `157`, naming the third tranche as landed and narrowing the next blocker to install-contract pointer neutralization.
- Downstream consumer statement on the face of the proposal: this tranche does not change `seed_migration_inventory.py` readers, does not change `harness_canary.py`'s call to `pu.build_progress_note(repo_root)`, and does not touch `tooling/codex/UPLIFT-HELD-LATER.md` as an artifact-home move.
