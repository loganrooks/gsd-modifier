# Propagation Registry System — Opus 4.7 Max R1

## How The Registry System Should Be Layered

- [d:r:i] The registry family currently reads as one hybrid surface (`14`) with one curated JSON slice (`13`, `artifacts/01-propagation-field-registry-v1.json`). That single surface does real work, and the widening it earns is not another flat artifact but a typed stack where each layer carries a distinct epistemic claim and refuses the claims that belong to another layer.
- [d:r:i] The stronger layered shape is five layers plus three gates:
  - **L0 Inventory roster** — maintained-doc upstream carry ([/home/rookslog/workspace/projects/get-shit-done-upstream/docs/INVENTORY.md](/home/rookslog/workspace/projects/get-shit-done-upstream/docs/INVENTORY.md:1)) and repo-local companion docs. Claim shape: *this shipped surface exists at this path under this family-slot at this version pin*. This layer does not reason about propagation.
  - **L1 Declared contracts** — authored declarations with machine-validated typing. [OVERLAY-MANIFEST.json](/home/rookslog/workspace/projects/prix-guesser/tooling/portable-gsd/overlay/OVERLAY-MANIFEST.json:1) plus [portable_gsd_contract.py](/home/rookslog/workspace/projects/prix-guesser/tooling/codex/portable_gsd_contract.py:40) is the prototype: authored ownership/typing on one side, deterministic validation/verification on the other. Claim shape: *this path has this declared role under this contract, and the contract is internally coherent today*.
  - **L2 AI-authored semantic map** — families, sub-family modes, cross-family edges, change-shape propagation obligations, named invariants, held-pressure roster. This is the layer that `08–13` already populate in prose and that `v1` currently compresses into JSON. Claim shape: *these carriers belong together as one family under this propagation mode; these edges cross families; these obligations fire when this change shape appears; these pressures are explicitly held rather than absorbed*.
  - **L3 Generated evidence** — runtime snapshots, fingerprints, manifest outputs, coherence reports, launch-truth captures, threshold-scan outputs. [project_uplift.py](/home/rookslog/workspace/projects/prix-guesser/tooling/codex/project_uplift.py:1), [runtime_visibility.py](/home/rookslog/workspace/projects/prix-guesser/tooling/codex/runtime_visibility.py:1), [portable_gsd_contract.py](/home/rookslog/workspace/projects/prix-guesser/tooling/codex/portable_gsd_contract.py:137), `manifest_install_coherence.py`, `capture_launch_truth.py`, `scan_threshold_language.py`. Claim shape: *under this basis commit, the state or fingerprint of this carrier or cross-surface alignment was observed this way*.
  - **L4 Operator / audit tooling** — the later tooling the registry enables: registry-snapshot diff, impact-adjacent reread suggestion, coverage parity against L0, lane-scoped slicing for audits. None of this exists yet; naming the layer gives the family a place to refuse to conflate it with L2 authorship.
- [d:r:i] The three gates sitting across the stack:
  - **G1 Coverage gate** — every L0 roster entry either lands in at least one L2 family/sub-family slot or is explicitly named as out-of-scope with a recorded reason. Silent omission is the failure shape.
  - **G2 Contract-coherence gate** — every L1 declared contract has a passing L3 validation output recorded at the basis commit. Unvalidated L1 is a shape that hides drift rather than carries it.
  - **G3 Refresh-inheritance gate** — every registry version records basis commit, source-note set, inherited dispositions, and the named held-pressures the refresh deliberately did not resolve.
- [e:c+r:i] The v1 artifact already performs L2 work (families, carriers, edges) and references its basis commit and source notes, which is the `G3` shape in partial form. Source: [artifacts/01-propagation-field-registry-v1.json](/home/rookslog/workspace/projects/prix-guesser/.planning/audits/2026-04-18-readiness-rerun-debrief-and-redesign/propagation-audit/artifacts/01-propagation-field-registry-v1.json:1). The widening is not to replace that surface but to type it so L0 entries, L1 entries, and L3 pointers no longer share one cell.
- [d:r:i] Read in layer terms, the registry family currently compresses L0, L2, and L3 into a single curated JSON plus a prose body. That compression lets one artifact ship, and it also blurs which claim is inventory-backed, which claim is AI-judged, which claim is machine-validated, and which claim is evidence-pointing. The layered shape preserves all four at once.

## What The Current Local Direction Still Flattens

- [d:r:i] **AI authorship is treated as one role.** `14` names `AI-authored` for the `families`, `carriers`, and `edges` of the registry. That phrasing compresses two roles that the layered view separates:
  - **Semantic mapping** (family membership, sub-mode split, edge direction/kind, invariants, held-pressure naming, change-shape obligations) — interpretive work where determinate tools can refuse to participate.
  - **Carrier annotation** (role labels, family slots, source-doc citation) — routine work that determinate tools can scaffold without usurping semantic decisions.
  A registry policy that calls both `AI-authored` without distinction understates how much of L2 can be scaffolded and how little of L2 can be delegated.
- [d:r:i] **Maintained-doc seeding is compressed to one relation.** `14` treats INVENTORY as a seed input. The stronger relations are coverage-contract ownership and family-slot mapping (see `What Maintained Docs Should Seed` above). A refresh that uses INVENTORY only as a seed loses the coverage signal that the roster entry was shipped and the registry remains silent about its fate.
- [d:r:i] **Runtime/tooling evidence is one bucket.** The seven sources above do seven epistemic jobs. Grouping them flattens when a registry row is backed by a whole-surface snapshot versus a lane-scoped observation, and when it is backed by a declared contract validation versus a sampled carrier fingerprint.
- [d:r:i] **Refresh is framed as one pipeline.** `14`'s seeding order (inventory -> broad docs -> runtime evidence -> prose audit family) reads as one top-to-bottom chain. The layered view distinguishes three refresh kinds that the current direction does not separate:
  - **Scheduled whole-registry refresh** — periodic regeneration at a new basis commit, consuming all four seed sources.
  - **Change-triggered slice refresh** — a specific L2 family or L1 contract moved, so the registry re-derives only that slice.
  - **Lane-scoped refresh** — a challenge lane needs a registry view at its own basis without committing to a new global version.
  Conflating these hides that scheduled refresh owes coverage re-verification, slice refresh owes edge revalidation, and lane-scoped refresh owes scope restriction so it does not silently overwrite global state.
- [d:r:i] **No explicit refusal surface.** `14`'s current direction does not name what the registry refuses to carry. Upstream-template drift detection, cross-runtime composition, aged-bespoke merge, whole-harness auto-extraction, and operator impact-suggestion are all load-bearing refusals today. Naming them as refusals (rather than gaps) clarifies the registry's boundary and preserves the held-later pressure instead of letting it ambient-drift into later refreshes.
- [d:r:i] **No stated coverage relation to `docs/INVENTORY.md`.** Because INVENTORY is authored as the authoritative shipped-surface roster, the propagation registry owes it a *mapped / held / out-of-scope* disposition for every entry. `14` says "seed from inventory" but does not yet say "a registry that omits a shipped surface silently is under-carrying the roster." That unstated relation is part of what lets later refreshes grow stale without the staleness being visible.
- [d:r:i] **The `v1` artifact carries load-bearing structure but is flat.** `artifacts/01-propagation-field-registry-v1.json` packs L0 path claims, L1 contract references, L2 semantic claims, and L3 implicit evidence in one object per carrier. That flat shape makes L2 revision entangled with L0 path updates (a carrier renaming or moving triggers a semantic-map rewrite) and hides which column of the layered stack actually moved. ## Stronger Design For The Propagation Registry Family

- [d:r:i] A stronger system design would carry the five layers, the three gates, and two small governing rules, and would represent the registry as a small bundle rather than one flat JSON. Concretely:
  - **`registry/v2/inventory-roster.json` (L0).** A coverage-oriented roster that cites `docs/INVENTORY.md` at its version pin, plus the repo-local rosters from `tooling/codex/README.md`, `OVERLAY-MANIFEST.json`, root/planning `AGENTS.md`, and workspace governance docs. Each entry has `source_doc`, `surface_family_slot`, `path`, `version_pin`. No semantic mapping lives here.
  - **`registry/v2/declared-contracts.json` (L1).** A typed index of authored contracts and their validators: `OVERLAY-MANIFEST.json` validated by `portable_gsd_contract.py`, the `UPLIFT-MANIFEST.json` schema validated by a future helper, any future declared contracts. Each entry has `contract_path`, `validator_path`, `last_valid_at_basis_commit`.
  - **`registry/v2/semantic-map.json` (L2).** Families, sub-family modes, carriers, edges, invariants, change-shape obligations, held-pressures, out-of-scope justifications, inheritance-from-v1. Each carrier row carries a `support_mode` column naming which lower-layer evidence backs it. This is the AI-authored layer.
  - **`registry/v2/evidence-index.json` (L3).** Pointers to the outputs: latest uplift manifest, latest runtime-visibility snapshot, latest overlay-contract validation, latest coherence report, per-lane launch-truth paths, latest scan outputs. Does not duplicate the outputs; indexes them at their basis commits.
  - **`registry/v2/coverage-and-refresh.json` (G1+G3).** One file that records, at the current basis, which L0 roster entries are `mapped`, `held-with-reason`, or `out-of-scope-with-reason`; the set of inherited dispositions from v1; and the named held-pressures this refresh does not resolve. This is the refresh-inheritance surface.
- [d:r:i] Two governing rules hold the bundle together:
  - **Layer-specific refresh discipline.** L0 is refreshed when maintained docs (INVENTORY, tooling README, overlay manifest) move. L1 is refreshed when declared-contract validators emit changes. L3 is refreshed when basis commits change or when a specific evidence tool is re-run. L2 is refreshed as the result of reading at least one of the above plus a prose reread, and requires explicit inheritance from the prior L2. G1 and G2 fire on every refresh; G3 fires at L2 refresh.
  - **Coverage-before-completeness.** A registry is considered usable when L0 coverage is explicit (every roster entry has a G1 disposition) and L1 contracts have passing L3a evidence. Silent omissions in either surface are a structural concern, even when the semantic map looks complete.
- [d:r:i] This shape preserves what `14` already earned — hybrid framing, curated slice discipline, AI-authored semantic work — and extends it by giving each part of the hybrid its own artifact, its own refresh trigger, and its own refusal surface. It does not yet introduce whole-harness auto-extraction (still held-later), upstream-template drift machinery (still held-later under `11`), cross-runtime composition (still held-later), or registry-to-impact suggestion tooling (still L4 and not opened).
- [d:r:i] The prose family (`08–14`) remains the interpretive layer and is strengthened by the layering rather than replaced. `08` stays the top-level field view; `09` stays the sub-family split; `10`–`12` stay the named invariants/edges; `13` stays the first-slice discipline note; `14` stays the generation and seeding policy and gains a `registry classes` section that names L0–L4 and the gates, replacing the current three-class compression.
- [d:r:i] Two additional surfaces the stronger design should name explicitly:
  - **A per-family roster-source column in L2.** Each family row declares which L0 roster entry owns discovery for that family (`governing_doctrine -> root+planning AGENTS.md`, `helper -> tooling/codex/README.md`, `install_overlay -> OVERLAY-MANIFEST.json`, `registry -> docs/INVENTORY.md plus .codex/agents/*.toml glob`, `launch_truth -> local audit governance`). That exposes which families are under-rostered today (e.g., launch-truth has no maintained-doc owner) and turns that visibility into a candidate backlog rather than an ambient gap.
  - **A refusal ledger.** A small section in the L2 or the coverage file listing what the registry deliberately does not attempt: whole-harness auto-extraction, declared-contract derivation without an author, launch-truth-to-registry comparison, upstream-pristine diff detection, cross-runtime topology mapping beyond `runtime_dirs_present`. Making refusals explicit keeps later refreshes from silently over-reaching.
- [d:r:i] Read this way, the registry family becomes a joined, typed view over already-maintained rosters and already-machine-validated contracts, with an explicit AI-authored compression layer, an explicit evidence-pointer layer, and explicit gates — rather than one flat JSON standing in for all five jobs at once.

## Bounded Next Design Move

- [d:r:i] The bounded move with the highest yield from the current baseline is **to split the v1 registry into the four typed files named above without introducing any new tooling, refresh cadence, or extraction logic**. Concretely:
  - Produce `registry/v2/inventory-roster.json` by reading `docs/INVENTORY.md`, `tooling/codex/README.md`, and `OVERLAY-MANIFEST.json` directly and emitting one roster entry per shipped surface with citation back to its source doc. No coverage claim yet — just the rostered paths.
  - Produce `registry/v2/declared-contracts.json` as a two-entry file (the overlay contract, the uplift manifest) pointing at their declarations and validators.
  - Produce `registry/v2/semantic-map.json` by migrating the current `v1` `families`/`carriers`/`edges` into the new shape, adding a `support_mode` column per carrier that cites which lower-layer evidence today backs it, and adding a `roster_source` column per family.
  - Produce `registry/v2/evidence-index.json` as a small pointer file naming the current `.planning/UPLIFT-MANIFEST.json`, latest runtime-visibility snapshot, latest overlay validation, latest coherence report, and latest launch-truth captures under the active audit.
  - Leave the `coverage-and-refresh.json` slot named but **held-later** for a subsequent move. Do not open G1 coverage enforcement in this bounded move; only stage its file slot so the later move does not need a structural precondition.
- [d:r:i] What this bounded move explicitly refuses:
  - It does not introduce whole-harness auto-extraction.
  - It does not introduce registry-diff tooling (L4 stays held).
  - It does not introduce upstream-pristine drift detection (stays held under `11`).
  - It does not attempt cross-runtime composition (stays held under the uplift held-later roster).
  - It does not claim full L0 coverage yet; G1 enforcement is staged but held.
- [d:r:i] Why this move is the right size now:
  - It preserves every semantic decision the `v1` slice already earned. No L2 work is thrown away.
  - It makes the compression visible. A later operator can see exactly which column of the registry moved on any refresh.
  - It sets up the cheapest next tool (registry diff between v2 snapshots) without requiring that tool to exist.
  - It gives the coverage gate a staged home before the gate is enforced, so the gate can be opened one family at a time rather than all at once.
  - It stays inside the prose family's current bounds — it is a typing pass over already-written content, not a widening into new propagation territory.
- [d:r:i] Alternative smaller moves, if the typed split is too large for the current slice:
  - **Smallest move A — support-mode column only.** Add a `support_mode` column to the existing `v1` carriers array, citing which lower-layer evidence backs each row. This lands the epistemic visibility benefit without restructuring the file.
  - **Smallest move B — roster-source column only.** Add a `roster_source` field per family in the existing `v1` families array. This lands the coverage-contract relation to INVENTORY and the helper README without opening L0 as its own artifact.
  - **Smallest move C — refusal ledger only.** Add a `refusals` section to `14` or to the `v1` artifact, naming what the registry does not attempt. This carries the boundary without requiring any schema change.
- [d:r:i] These smaller moves compose — they are the first three columns/sections the full typed split would land anyway — so picking them in order is itself a bounded rollout of the stronger design.
