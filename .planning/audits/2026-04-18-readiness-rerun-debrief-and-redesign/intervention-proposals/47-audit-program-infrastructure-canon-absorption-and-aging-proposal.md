# Audit-Program Infrastructure, Canon Absorption, And Aging Proposal

## Purpose

- [g:r:i] This proposal defines the bounded audit-program infrastructure family exposed by the full-field harness-improvement map.
- [g:r:i] The target is not to rewrite every audit subtree at once. The target is to give recurring audit work a cleaner inheritance path, a clearer canon-absorption rule, and a better aging/graduation protocol.

## Proposed Components

- [d:r:i] A compact audit-lane pattern library.
  - scope:
    - packet
    - spec
    - prompt
    - launch-truth
    - output
    - inheritance / disposition
  - purpose:
    - reduce repeated scaffold reconstruction
    - keep anti-misread and launch-truth discipline portable across audit families

- [d:r:i] A canon-absorption protocol.
  - scope:
    - when a landed intervention family should move doctrine into root/planning governance or helper docs
    - when it should remain as audit-local history
  - purpose:
    - reduce doctrine density by making absorption explicit rather than accidental
    - stop live doctrine from remaining trapped in temporary subtree notes

- [d:r:i] An audit-subtree aging and graduation note.
  - scope:
    - how to treat old audit families as active, aging, graduated, superseded, or archive-ready
  - purpose:
    - prevent long-lived audit subtrees from becoming permanent ambiguous storage

## Why This Family Matters

- [d:r:i] This workspace already carries many audit families with repeating structure.
- [d:r:i] The current system works, but repeated scaffold authoring and ad hoc canon uplift both create maintainability drag.
- [d:r:i] This family raises maintainability and operator control without forcing the next intervention family to rediscover scaffolding and absorption rules from memory.

## Held For Later

- [d:r:i] Cross-vendor reviewer inheritance can be part of this family later, but it should not be forced into the first slice if that would delay the pattern library, canon-absorption rule, or aging protocol.
- [d:r:i] Broader automation around audit aging also stays later. The first slice should be doctrine and routing, not a new archival engine.

## Current Consequence

- [d:r:i] If accepted, this family should follow the canary family and sharpen how later audit work remains durable without bloating root governance or letting subtrees age without clear status.
