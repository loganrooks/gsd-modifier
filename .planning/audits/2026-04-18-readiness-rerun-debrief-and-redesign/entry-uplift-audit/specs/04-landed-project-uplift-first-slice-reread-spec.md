# Landed Project Uplift First-Slice Reread Spec

## Framing

- [g:r:i] Reread the landed project-uplift first slice after implementation.
- [g:r:i] The governing task is not to reopen generic terrain discovery, not to restage the earlier bundle challenge, and not to flatten the family back into onboarding talk.
- [g:r:i] The governing task is to judge the live slice in its current form:
  - what it now carries more strongly
  - where the live implementation boundary still thins or compresses distinct jobs
  - what should still stay explicit later-family work
  - which adjacent strengthening route should come next
- [g:r:i] Keep the review out of threshold language, deficit-only framing, and binary recommendation shapes.

## Primary Questions

1. What does the landed first slice now carry more strongly than the pre-implementation bundle?
2. Which parts of the live helper/workflow/output chain now have stronger local form because implementation is real rather than proposed?
3. Where do the helper, workflow, outputs, or `progress` consumer still thin, blur, or compress distinct jobs that should stay more explicit?
4. What do the landed mechanics improve in live use:
   - posture classification
   - durable uplift memory
   - thin manifest carry
   - read-only `progress` consumption
   - detect-only routing
5. Which remaining revision, if any, would still materially strengthen the landed slice before additive install routes or later cross-runtime widening?
6. Which later families should remain explicit later-family work rather than being pulled into this slice?
7. Which adjacent strengthening route should come next, and why?

## Required Output Shape

Use these exact section headings:

1. `What The Landed First Slice Now Carries More Strongly`
2. `Where The Live Implementation Boundary Still Thins Or Compresses Distinct Jobs`
3. `What The Landed Mechanics Improve In Live Use`
4. `What Still Deserves Revision Before Wider Follow-Through`
5. `Later Families To Keep Explicit`
6. `Strongest Adjacent Strengthening Route`
7. `How This Landed Slice Should Be Inherited`

Inside section `7`, separate:
- `Carry Forward`
- `Revise Before Widening`
- `Hold For Later`

## Review Discipline

- [d:r:i] Challenge the landed slice from the actual current surfaces, not from memory of the proposal bundle alone.
- [d:r:i] Keep the review concrete about which live mechanics now increase carry and which still need sharpening.
- [d:r:i] Do not collapse helper logic, workflow ownership, durable outputs, and consumer routing into one blurred comment.
- [d:r:i] If you think the next strengthening route should stay within the landed slice, name the narrow surface and the reason in terms of carry, routing, operator legibility, or future leverage.
- [d:r:i] If you think additive install or cross-runtime widening should still wait, keep that later-family hold explicit rather than implying a silent veto.
- [d:r:i] If you think verification should widen, make the widened verification route specific.
