# 02 GSD Lifecycle And Long-Arc Layer Audit - Task Spec

## Purpose

Audit the repo-local GSD layer as found in:

- `.codex/get-shit-done/`
- `tooling/portable-gsd/overlay/`
- relevant repo-local skills and config

The focus is whether this layer can actually carry long-horizon doctrine, preserved seams, future-aware planning, and non-foreclosure discipline through the repo's lifecycle rather than only through phase-local planning.

## Core Question

How well does the repo-local GSD stack integrate `LONG-ARC.md`, future-awareness, preserved seams, reversal-sensitive boundaries, and doctrine-sensitive checkpoints across:

- new project
- new milestone
- progress
- transitions
- planning
- execution
- completion
- skill/command usage

## Motivating Grounds

This lane exists because the user explicitly asked whether the framework in `.codex` can support:

- long-term, future-aware design
- a strong relationship to `LONG-ARC.md`
- day-to-day execution that still respects farther-horizon doctrine

## Specific Questions

1. Where is `LONG-ARC.md` already first-class?
2. Where is it phase-strong but lifecycle-weak?
3. Which existing workflows or templates should be patched rather than replaced?
4. Which missing capabilities should become:
   - workflow changes
   - template changes
   - repo-local skill additions
   - command changes
5. How should the repo-local GSD layer better support:
   - future-aware planning
   - doctrine carry-forward
   - explicit preserved seams
   - non-foreclosure
   - milestone-to-long-arc translation

## Output Requirements

- current lifecycle integration map
- strongest existing leverage points
- weakest lifecycle gaps

## Anti-Misread Rules

- Do not treat `LONG-ARC.md` as a second roadmap.
- Do not recommend pulling long-arc doctrine into every workflow indiscriminately.
- Distinguish:
  - `carry-forward awareness`
  - `scope widening`
- Do not turn this into a generic GSD redesign memo. Keep it repo-specific.
