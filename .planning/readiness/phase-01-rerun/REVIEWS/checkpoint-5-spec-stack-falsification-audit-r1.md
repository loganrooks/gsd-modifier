# Checkpoint 5 Spec Stack Falsification Audit R1

## Verdict

- status: `revise-before-implementation`
- explanation:
  - [d:c+r:i] The current Checkpoint 5 candidate stack is not yet strong enough to guide implementation. The strongest justified criticism is that it still behaves as if "four `.codex` workflows plus selective wrapper touch-ups" is the whole follow-through surface, even though the repo's actual runtime/install topology, chain-tail artifact/state surfaces, and runtime-authoritative agent prompts still carry unowned propagation consequences. Sources: `.planning/readiness/phase-01-rerun/AUDITS/checkpoint-5-reactivated-launch-spec.md:24-43`; `.planning/readiness/phase-01-rerun/AUDITS/checkpoint-5-workflow-follow-through-implementation-spec.md:23-55`; `AGENTS.md:5-9`; `scripts/setup-portable-gsd.sh:10-31`; `.planning/readiness/phase-01-rerun/AUDITS/checkpoint-4-gsd-workflow-chain-and-artifact-contracts-excellence.md:7,45-53,63-75`.

## Findings

1. [e:c+r:i] Severity: `critical` - portable overlay / reinstall propagation is already an active dependency, not a true deferral. The repo's governing runtime uses live `.codex/get-shit-done`, but the supported install path is `./scripts/setup-portable-gsd.sh`, which reinstalls local GSD and then copies every tracked overlay file into `.codex/`. The candidate spec nevertheless proposes patching `.codex/get-shit-done/workflows/execute-phase.md` and several wrapper skills after workflow edits land, while the tracked overlay/update contract currently covers only `gsd-discuss-phase`, `discuss-phase.md`, `research-phase.md`, `plan-phase.md`, and a small template/config set. It does not presently cover `execute-phase.md`, `gsd-plan-phase`, `gsd-review`, or `gsd-execute-phase`. That means the spec's own requested edits would create live-only truth or reinstall regressions unless overlay coverage and regeneration doctrine widen first. Treating `R5.7 portable GSD reproducibility / provenance hardening` as merely conditional is therefore already false for this candidate stack. Sources: `AGENTS.md:5-9`; `scripts/setup-portable-gsd.sh:10-31`; `.planning/readiness/phase-01-rerun/AUDITS/checkpoint-5-reactivated-launch-spec.md:27-33`; `.planning/readiness/phase-01-rerun/AUDITS/checkpoint-5-workflow-follow-through-implementation-spec.md:37-45`; `tooling/portable-gsd/README.md:40-56`; `.planning/research/2026-04-15-orchestration-framework-audit/02-long-arc-lifecycle-integration-audit.md:112-128`; `.planning/readiness/phase-01-rerun/TASKS.md:28-31`.

2. [e:c+r:i] Severity: `critical` - the candidate still overfits to four named workflows and leaves the accepted chain tail unowned. Checkpoint 4 explicitly scoped this lane through `verify-work/UAT` plus the shared contracts `SUMMARY.md`, `VERIFICATION.md`, `HUMAN-UAT.md`, and `UAT.md`. The reactivated scope and implementation spec then narrow concrete follow-through to `discuss-phase`, `research-phase`, `plan-phase`, `execute-phase`, and four wrapper skills. That narrowing is not harmless. `verify-work` defines `status: partial` as an unresolved testing state; `execute-phase` still allows `"approved"` on human-needed verification to proceed directly into `update_roadmap`; `phase complete` then marks the roadmap checkbox and status row `Complete` while treating `partial` and `human_needed` only as warnings; `progress.md` separately routes `uat_partial` as incomplete testing; and `init.cjs` still counts phases with summaries as completed. Tightening "debt-carrying completion" only inside `execute-phase.md` would therefore leave contradictory closure semantics across roadmap, state, progress, UAT, and milestone-counting surfaces. Sources: `.planning/readiness/phase-01-rerun/AUDITS/checkpoint-4-gsd-workflow-chain-and-artifact-contracts-excellence.md:7,45,73`; `.planning/readiness/phase-01-rerun/AUDITS/checkpoint-5-reactivated-launch-spec.md:27-33`; `.planning/readiness/phase-01-rerun/AUDITS/checkpoint-5-workflow-follow-through-implementation-spec.md:35-45`; `.codex/get-shit-done/workflows/verify-work.md:363-377`; `.codex/get-shit-done/workflows/execute-phase.md:1044-1058,1086-1114`; `.codex/get-shit-done/bin/lib/phase.cjs:673-725`; `.codex/get-shit-done/workflows/progress.md:153-201,328-349`; `.codex/get-shit-done/bin/lib/init.cjs:771-776`.

3. [e:c+r:i] Severity: `high` - Track A is still being over-credited as valid partial implementation even though the runtime-authoritative worker prompts still encode a legacy steering model. The reactivated scope says the `.toml` alignment work remains valid checkpoint input. But the researcher prompt still tells the agent to parse `## Decisions`, `## Claude's Discretion`, and `## Deferred Ideas`, then requires `## User Constraints` as the first RESEARCH section and explicitly says "Be prescriptive, not exploratory." The planner prompt still anchors context fidelity on `## Decisions`, `## Deferred Ideas`, and `## Claude's Discretion`. The plan-checker still parses only `Decisions, Claude's Discretion, Deferred Ideas` for context compliance. The current steering-brief contract is materially broader: `Implementation Decisions`, `the agent's Discretion`, `working_model`, `derived_constraints`, `open_questions`, `epistemic_guardrails`, `canonical_refs`, and `future_awareness` are all first-class inputs. That mismatch is not a naming nit. It means the supposedly aligned phase-critical agents are still structurally biased to under-read exactly the categories this checkpoint is trying to preserve and propagate. Sources: `.planning/readiness/phase-01-rerun/AUDITS/checkpoint-5-reactivated-launch-spec.md:26`; `tooling/portable-gsd/overlay/agents/gsd-phase-researcher.toml:46-72`; `tooling/portable-gsd/overlay/agents/gsd-planner.toml:52-81`; `tooling/portable-gsd/overlay/agents/gsd-plan-checker.toml:48-61,284-294`; `.codex/get-shit-done/templates/context.md:30-110`; `.planning/readiness/phase-01-rerun/AUDITS/checkpoint-5-workflow-follow-through-implementation-spec.md:25-41`.

4. [e:c+r:i] Severity: `high` - `gsd-research-phase` is an active dependency, not optional wrapper polish. The implementation spec schedules wrapper follow-through only for `gsd-discuss-phase`, `gsd-plan-phase`, `gsd-review`, and `gsd-execute-phase`. But `gsd-research-phase` is not a thin wrapper that merely points at `workflows/research-phase.md`; it embeds its own orchestration, files-to-read contract, downstream consumer contract, and success handling directly inside the skill. Its prompt still loads only requirements/context/state, omits resolved `canonical_refs`, omits explicit `future_awareness` / `epistemic_guardrails` handling, and still frames the downstream output in the older prescriptive section set. If `research-phase.md` changes but `gsd-research-phase` does not, the repo retains a stale standalone research lane that bypasses the tightened research contract. Sources: `.planning/readiness/phase-01-rerun/AUDITS/checkpoint-5-workflow-follow-through-implementation-spec.md:25-27,43-45`; `.codex/skills/gsd-research-phase/SKILL.md:48-61,74-186`; `.codex/get-shit-done/workflows/research-phase.md:48-79,90-94`.

5. [d:c+r:i] Severity: `medium` - the candidate has not yet decided where the stronger steering-to-plan obligation becomes auditable inside the plan artifact contract itself. The implementation spec wants planning to preserve material decisions, open questions, and protected seams without introducing a heavier trace subsystem. The current PLAN contract guarantees `future_preservation` and `must_haves`, but it does not reserve any explicit carrier for open-question disposition, preserved-decision exceptions, or defer/escalate rationale. That may still be acceptable, but only if the candidate explicitly argues that the existing fields are sufficient and the checker/review surfaces will enforce the mapping. Right now that carrier decision is implicit, which leaves later audit likely to re-litigate whether the new obligation is real or just stronger prose pressure. ## What Must Change Before Implementation

- [d:r:i] Promote overlay/install propagation from `conditional` to `required`. Either widen tracked overlay coverage and its regeneration doctrine for every live `.codex` file the checkpoint will touch, or explicitly narrow the checkpoint away from any surface that lacks tracked overlay truth.
- [d:r:i] Widen the candidate scope from "four workflows" to the accepted chain tail that actually carries closure semantics: `verify-work.md`, `phase complete` / roadmap update machinery, progress/state/milestone-count surfaces, and any UAT/verification artifact contracts whose statuses are supposed to distinguish clean versus debt-carrying completion.
- [d:r:i] Reopen Track A as semantic alignment, not just AGENTS-surface alignment. Researcher, planner, and checker prompts need to consume the current steering-brief categories and the checkpoint's new research-disposition semantics, not merely point at the right repo docs.
- [d:r:i] Add `gsd-research-phase` to wrapper alignment and update its embedded process directly. It cannot stay out of scope while research adequacy/disposition is a primary checkpoint seam.
- [d:r:i] Decide explicitly whether the new steering-to-plan obligation is carried by existing `future_preservation` / `must_haves` fields plus checker enforcement, or whether one bounded additional carrier is required. Do not leave that decision ambient.

## What Can Remain Deferred

- [d:c+r:i] Broad install pinning can remain deferred if and only if the touched runtime files are fully represented in tracked overlay truth. The current candidate has not met that condition yet.
- [d:c:i] Broad branch/worktree redesign can remain deferred unless the eventual patch set materially changes worktree/config behavior or later verification exposes a concrete mismatch. Sources: `.planning/readiness/phase-01-rerun/TASKS.md:29`; `.planning/readiness/phase-01-rerun/STATUS.md:80-82`.
- [d:c:i] A dedicated repo-local cross-model audit skill and a non-phase external-reread protocol/template can remain deferred unless later checkpoints show repeatable non-phase protocol gaps that current top-level orchestration cannot carry cleanly. Sources: `.planning/readiness/phase-01-rerun/TASKS.md:31`; `.planning/readiness/phase-01-rerun/PLAN.md:173-190`.
- [d:c:i] Exhaustive skill-family enumeration can remain deferred beyond the directly implicated surfaces. But `gsd-research-phase` no longer qualifies as safely deferrable because the candidate's own requested change set makes it directly implicated.

## Propagation Consequences

- [d:r:i] If `research-phase.md` changes its adequacy/disposition contract, the update set is not just `.codex/get-shit-done/workflows/research-phase.md`. It also reaches `tooling/portable-gsd/overlay/get-shit-done/workflows/research-phase.md`, `tooling/portable-gsd/overlay/agents/gsd-phase-researcher.toml`, and `.codex/skills/gsd-research-phase/SKILL.md`.
- [d:r:i] If `plan-phase.md` changes steering-traceability expectations, decide whether `templates/phase-prompt.md` and its overlay copy are the audit carrier or whether checker/review surfaces alone will enforce the mapping. Do not let that remain implicit.
- [d:r:i] If `execute-phase.md` changes clean-versus-debt completion semantics, the repo must also review `verify-work.md`, `.codex/get-shit-done/bin/lib/phase.cjs`, `.codex/get-shit-done/workflows/progress.md`, and `.codex/get-shit-done/bin/lib/init.cjs`, because those surfaces currently emit, count, or present the same completion states differently.
- [d:r:i] If any live `.codex` workflow or wrapper file changes, `tooling/portable-gsd/README.md` and the tracked overlay tree must remain truthful enough that `./scripts/setup-portable-gsd.sh` can reproduce the checkpoint's intended runtime on a fresh machine.

## Change Summary

- [d:c+r:i] The current candidate stack is directionally stronger than the pre-reactivation bundle, but it is still under-scoped in exactly the places a later strong audit would attack first: tracked-versus-live runtime truth, chain-tail closure semantics, semantic worker-prompt alignment, and standalone research entrypoints.
- [d:r:i] Implementation should not begin until the checkpoint either widens to own those propagation surfaces or explicitly narrows away from them with a scrutiny-resistant argument. Right now it does neither, which makes the stack look more bounded than it really is.
