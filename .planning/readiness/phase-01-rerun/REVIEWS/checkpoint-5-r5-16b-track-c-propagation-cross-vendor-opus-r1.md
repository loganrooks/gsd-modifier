# Checkpoint 5 R5.16b Track C Propagation Cross-Vendor Opus R1

## Research Frame

- Mode: independent cross-vendor `gap-exposure` + `completeness-challenge` read of Track C.
- Question: whether current Track C candidate changes propagate launch-truth, closure-status, and debt-carrying-completion semantics into the consumers that actually decide completion and forward motion, under the strongest justified pre-rerun standard.
- Method: direct re-verification of every load-bearing citation rather than summarization of internal r1; independent identification of blind spots at the spec's declared read-set boundary; explicit two-sided non-promotion test per `POST-FALSIFICATIONIST-REVIEW-DOCTRINE.md:134-140`.

## Blocking Propagation Gaps

1. [e:c+r:i] **`human_needed` cannot stay `human_needed` once the user types `approved`.** `execute-phase.md` writes `{phase_num}-HUMAN-UAT.md` with `status: partial`, tells the user that debt will appear in later audits, and on a bare `"approved"` proceeds directly to `update_roadmap`; `phase complete` then scans UAT/VERIFICATION for debt markers but records them only in a `warnings` array while still flipping the ROADMAP checkbox to `[x]` and the progress table cell to `Complete` with today's date. Because `roadmap.cjs` later treats that checkbox as the trusted routing authority over disk evidence, every downstream status/progress surface reads the phase as `complete` regardless of the `HUMAN-UAT.md` partial. This directly contradicts the active Checkpoint 5 requirement that debt-bearing completion and clean completion stay distinct. Sources: `.codex/get-shit-done/workflows/execute-phase.md:1263-1321,1347-1375`; `.codex/get-shit-done/bin/lib/phase.cjs:771-789,802-824`; `.codex/get-shit-done/bin/lib/roadmap.cjs:176,186-195`; `.planning/readiness/phase-01-rerun/GATES/checkpoint-5.md:82-91`; `.planning/readiness/phase-01-rerun/STATUS.md:92-114`; `.planning/readiness/phase-01-rerun/AUDITS/checkpoint-5-workflow-follow-through-implementation-spec.md:98-100`.

2. [e:c+r:i] **Override-backed acceptance is doctrinally flattened into `status: passed`, and the verifier TOML cannot emit anything else.** `verification-overrides.md` states explicitly that `PASSED (override)` items count toward the passing score, not the failing score, and that `A phase with all items either VERIFIED or PASSED (override) can have status passed`. The overlay verifier TOML's Step 9 decision tree has exactly three terminal states — `passed`, `gaps_found`, `human_needed` — with no `verified_with_debt` slot, so the agent is structurally incapable of emitting a debt-bearing completion state. The advisory `if more than 2-3 items need overrides, revisit the plan instead of overriding in bulk` rule is not enforced anywhere in the verifier, in `audit-uat`, or in progress routing. So intentional-but-debt-carrying deviations disappear from every scannable status surface. Sources: `.codex/get-shit-done/references/verification-overrides.md:56-60,105-132,204-226`; `tooling/portable-gsd/overlay/agents/gsd-verifier.toml:174-198,486-500`; `.codex/get-shit-done/bin/lib/phase.cjs:785-789`; `.codex/get-shit-done/bin/lib/commands.cjs:12-35`; `.planning/readiness/phase-01-rerun/AUDITS/checkpoint-5-workflow-follow-through-implementation-spec.md:98-100`.

3. [e:c+r:i] **Routing authority ignores verification state once the checkbox is flipped.** `roadmap.cjs` computes phase `disk_status` purely from `summaryCount >= planCount` and then explicitly prefers the ROADMAP checkbox over disk when they disagree (`If roadmap marks phase complete, trust that over disk file structure`). `progress.md` compounds this by declaring its cross-phase `Verification Debt` banner `a WARNING, not a blocker — routing proceeds normally`. The `determinePhaseStatus` helper in `commands.cjs` that actually distinguishes `Complete`, `Needs Review`, and `Executed` is never called by the routing paths in `progress.md` or `transition.md`; it is only used where the phase-status command path reaches it. So the one location in the runtime that has debt-aware vocabulary is isolated from the authority that decides next-phase movement. Sources: `.codex/get-shit-done/bin/lib/roadmap.cjs:176-208`; `.codex/get-shit-done/workflows/progress.md:168-203,342-440`; `.codex/get-shit-done/bin/lib/commands.cjs:12-35`; `.codex/get-shit-done/bin/lib/phase.cjs:792-824`.

4. [e:c+r:i] **Chain-tail consumers beyond the spec's read set independently repeat the same cheap-closure semantics.** `verify-work.md` auto-transitions to phase completion when `issues==0` and offers only a `Proceed anyway?` acknowledgement when open artifacts remain. `transition.md` explicitly states `This does NOT block transition — it ensures the user sees the debt before confirming`, and in yolo mode auto-approves completion. `ship.md` accepts `status: human_needed` with human approval as ship-ready. `autonomous.md` offers `Continue without validation` for `human_needed`, `Continue without fixing` for `gaps_found`, and `Continue anyway` for persistent gap closure failure, then routes to the next iterate step in all three branches. That is four chain-tail workflows outside the audit spec's listed consumer set independently converging on `visible-but-non-blocking` closure pressure. Sources: `.codex/get-shit-done/workflows/verify-work.md:413-459,461-486`; `.codex/get-shit-done/workflows/transition.md:77-99,101-122`; `.codex/get-shit-done/workflows/ship.md:41-46`; `.codex/get-shit-done/workflows/autonomous.md:411-472`.

5. [e:c+r:i] **The executor-side producer contract has no slot to emit debt-carrying completion.** The agent-contracts Executor→Verifier schema specifies only `phase, plan, subsystem, tags, key-files, metrics` for the SUMMARY frontmatter; the SUMMARY template matches and has no `status` or `completion_mode` field. The overlay executor TOML's summary creation section writes Deviations as prose and asks only for a self-check `PASSED`/`FAILED` at the bottom. So even an executor that correctly noticed it had auto-added a Rule-2 security shim that should carry downstream as scope debt has no mechanical channel to express that — the signal must survive by prose parsing that no routing code performs. This is upstream of every consumer gap: the producer cannot produce the missing signal even if the doctrine is updated. ## Local But Important Gaps

- [e:c+r:i] **`capture_launch_truth.py` renders `--since` and `--latest` captures with identical `matched` language.** The `summarize_field` helper produces the same `matched requested X across N/M captured rows` line regardless of boundary mode; the `--latest` weakness is surfaced only as a trailing caveat bullet in the footer. A reviewer quoting the assessment section into a readiness artifact loses the boundary-mode distinction. The WORKFLOW.md doctrine at lines 78-82 is stronger than the helper's own rendering. Fix locality: the helper's renderer, not the consumers. Sources: `tooling/codex/capture_launch_truth.py:204-232,358-369`; `WORKFLOW.md:71-82`.

- [e:c+r:i] **Partial requested-sets still render positive `matched` language.** `has_comparison_inputs` accepts a capture where only one `--requested-*` field was supplied. The generated assessment then renders `matched X/Y` for the one field and silently omits any line for the unsupplied fields — it does not say `not captured; unverifiable from this artifact`. Doctrine in `AI-GUARDRAILS.md:89-91` is that missing runtime fields stay unresolved, but the helper allows the input side to stay silently thin. Sources: `tooling/codex/capture_launch_truth.py:45-47,204-218,375-392`.

## Signals That The Problem May Already Be Wider

- [e:c+r:i] **Eight surfaces independently encode closure pressure without a shared debt concept.** The cheap-closure pattern repeats across `gsd-verifier.toml` (three-terminal decision tree), `verification-overrides.md` (override-to-passing flattening), `phase.cjs` (warnings-only), `roadmap.cjs` (checkbox-trumps-disk), `progress.md` (debt banner is non-blocking by doctrine), `transition.md` (`does NOT block transition`), `ship.md` (`human_needed` with human ack is ship-ready), and `autonomous.md` (three `continue anyway` branches). No one of these is the wrong place to represent completion; the fact that all eight independently picked the same cheap semantics without converging on a debt state is a governance-level convergence, not a local propagation drift. One patched surface will not rehome the other seven. Sources: as cited in blockers 1-4 plus `tooling/portable-gsd/overlay/agents/gsd-verifier.toml:486-500`.

- [e:c+r:i] **The Track C spec's read set was materially inadequate under the package's own standard.** `POST-FALSIFICATIONIST-REVIEW-DOCTRINE.md:93-98` requires specs to `distinguish candidate, consumer, and chain-tail / representation surfaces where propagation matters`. The spec listed nine consumers plus five candidates; the governance semantics actually live in at least four additional chain-tail files (`transition.md`, `ship.md`, `autonomous.md`, `complete-milestone`-adjacent progress routing) and three library files (`phase.cjs`, `roadmap.cjs`, `commands.cjs`). An audit that did not reach those surfaces could not have judged locality honestly. Any future R5.16 spec bundle should add a read-adequacy seam expansion rule. Sources: `.planning/readiness/phase-01-rerun/POST-FALSIFICATIONIST-REVIEW-DOCTRINE.md:93-98`; `.planning/readiness/phase-01-rerun/REVIEWS/checkpoint-5-r5-16b-track-c-propagation-audit-spec.md:32-50`.

- [e:c+r:i] **The `determinePhaseStatus` helper proves the vocabulary is already known but is not load-bearing.** `commands.cjs:15-36` correctly distinguishes `Complete`, `Needs Review`, and `Executed` based on VERIFICATION.md status. That code exists, ships, and is internally coherent — it just is not the code path that governs next-phase routing, checkbox flipping, or roadmap status cells. The problem is not absent vocabulary; the problem is that a governance standard to make that vocabulary authoritative has not been promulgated. Promulgating it is larger than a three-file Track C patch. Sources: `.codex/get-shit-done/bin/lib/commands.cjs:12-35`; `.codex/get-shit-done/bin/lib/phase.cjs:802-824`; `.codex/get-shit-done/bin/lib/roadmap.cjs:176-208`.

## What Must Change Before Track C Can Count As Closure-Ready

These are all blocking. Debt-aware routing cannot exist unless they move together; patching any one surface in isolation will not clear the contradiction.

1. A single load-bearing `completion_mode` (clean vs debt-bearing) must become a first-class state in VERIFICATION.md frontmatter, emitted by the verifier's decision tree, and consumed by `phase complete` so the ROADMAP checkbox flip and progress-table cell reflect it.

2. `roadmap.cjs:176,193-195` must consult `completion_mode` rather than treating `summaryCount >= planCount` or the bare checkbox as the routing authority. `progress.md` `Verification Debt` section must become blocking for debt-bearing phases, not a trailing banner.

3. `execute-phase.md:1263-1321` must not accept a bare `"approved"` response as the trigger for `update_roadmap` unless the resulting completion carries the debt-bearing mode forward. The `HUMAN-UAT.md status: partial` write is insufficient by itself because the checkbox authority overrides it downstream.

4. `verification-overrides.md:105-132` and `gsd-verifier.toml:486-500` must either remove the rule that overrides count toward the passing score, or add a `completion_mode: debt_bearing` emission when `overrides_applied > 0`. The advisory `2-3 override` threshold at `verification-overrides.md:56-60` needs enforcement, not prose.

5. `transition.md:77-99`, `ship.md:41-46`, and `autonomous.md:411-472` must each consume the new completion mode or be explicitly documented as contradictions that Track C leaves open. `This does NOT block transition` is a knowing policy statement that directly conflicts with the active Checkpoint 5 requirement.

6. `agent-contracts.md:70-78` and `templates/summary.md:10-46` must expose a structured completion-mode field in the Executor→Verifier contract so that executor-side scope decisions (Rule-2 auto-adds, fix-attempt-limit deferrals, authentication gates) can surface mechanically rather than through prose parsing.

7. `capture_launch_truth.py:204-232,358-369` must differentiate `--since` and `--latest` in the assessment lines themselves, not only in a footer caveat. The rendered `matched X/Y` language should be different text in the two modes, so downstream artifacts cannot quote the assessment section as if the capture were certification-grade when it was latest-guess.

8. If Track C stays bounded to the three candidate files plus two TOMLs, the audit bundle must add an explicit `Known Unfixed Propagation Contradictions` appendix to `GATES/checkpoint-5.md` that names items 2-6 above and the specific line ranges where the contradiction lives, so they cannot be re-litigated as surprises in later audits. Leaving the contradictions unnamed would itself be a post-falsificationist closure failure.

## What Can Remain Local

- `capture_launch_truth.py` can remain a capture aid rather than a provenance subsystem once its rendering is sharpened on the `--latest`/`--since` distinction. Broader portability/provenance hardening stays deferred.

- The two overlay TOMLs can remain Track C's editing surfaces *if* the downstream routing code path in section `What Must Change` moves in the same slice. Otherwise they are stranded and Track C re-opens.

- SKILL.md wrapper files do not need doctrinal changes; they propagate whatever the workflows embed. Keeping them untouched in this slice is acceptable.
