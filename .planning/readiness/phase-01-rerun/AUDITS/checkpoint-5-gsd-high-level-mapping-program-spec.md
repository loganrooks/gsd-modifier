# Checkpoint 5 GSD High-Level Mapping Program Spec

## Purpose

Implement the iterative, emergent-first high-level GSD mapping program the user asked for.

This program exists because the current high-level picture is still too simple to support later zooms, later intervention analysis, or clean reasoning about what has already been modified locally.

The program must:

- broaden the high-level inventory first
- separate repo-local runtime reality from clean upstream baseline truth
- distinguish version-matched upstream baseline from later upstream trajectory
- derive ontology from repo evidence rather than presupposing one
- preserve surfaces that do not fit any current grouping
- challenge the resulting map before authorizing deeper work

It must not:

- jump into family deep-dives yet
- force all surfaces into a neat taxonomy
- treat older checkpoint maps as sovereign truth
- let awkward or cross-cutting surfaces disappear

## Persistent Anti-Misread Rules

- `unplaced`, `ambiguous`, and `cross-cutting` are valid results
- missing coverage is not the same thing as irrelevance
- repo-local readiness control surfaces are not runtime canon
- live materialized runtime is not automatically the same as tracked overlay truth
- repo-local inventory is not automatically the same thing as clean upstream truth
- version-matched upstream baseline is not automatically the same thing as future upstream trajectory
- a cleaner-looking diagram is not automatically a truer one
