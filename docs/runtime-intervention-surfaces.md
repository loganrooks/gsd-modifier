## Runtime-Facing Carriers

The runtime-facing carrier set has four families.

First, `tooling/portable-gsd/overlay/OVERLAY-MANIFEST.json` is the source contract that says which source files materialize into which runtime targets. Schema 3 entries carry `capability_id`, `parity_tier`, and per-runtime `materializers`.

Second, `tooling/portable-gsd/overlay/` carries the bulk shared and Codex-specific payload: workflows, references, templates, runtime libraries, Codex skills, Codex `config.toml`, agent Markdown, agent TOML, and compact prompts.

Third, `harness_modifier/overlay/` carries modifier-owned specialist workflows, Codex skill adapters, Claude command wrappers, and helper shims that the manifest maps into runtime roots.

Fourth, generated runtime roots `.codex/` and `.claude/` are the live outputs after setup. They are not present in this isolated worktree, so this inventory records their expected role from contracts and setup scripts rather than live observation.

## Instruction Generation Paths

`tooling/portable-gsd/overlay/get-shit-done/workflows/new-project.md` is the visible initialization producer for project instruction files and planning surfaces. The evidence pass found that it currently uses `AGENTS.md` as the instruction filename for all runtimes.

`tooling/codex/project_uplift.py` is not the root instruction generator. It is the durable uplift posture producer: it reads the carrier catalog, fingerprints carrier state, and can write `.planning/UPLIFT-REPORT.md`, `.planning/UPLIFT-MANIFEST.json`, and the uplift section in `.planning/STATE.md`.

`harness_modifier/uplift/carrier_catalog.json` defines which instruction, doctrine, runtime-registry, and marker carriers are relevant to uplift. That makes catalog edits contract edits, because they change what later reports and progress views consider authoritative or drift-sensitive.

Runtime materialization is also part of the instruction path for Codex config and prompt behavior. `tooling/portable-gsd/overlay/config.toml` includes `experimental_compact_prompt_file = "__COMPACT_PROMPT_FILE__"`, and setup/contract code chooses and renders the compact prompt before writing runtime config.

## Materialization And Install Paths

The maintained install path is `scripts/setup-portable-gsd-runtime.sh --runtime codex|claude|both`.

For each selected runtime it:

1. Runs upstream local GSD install for that runtime.
2. Captures pristine overwrite copies for overwrite-mode manifest entries.
3. Validates the overlay manifest.
4. Applies the tracked overlay with project-root and compact-prompt substitution.
5. Applies repo-local reasoning defaults where applicable.
6. Verifies materialized overlay coherence.

`scripts/setup-portable-gsd.sh` remains a Codex-only shortcut into this path. It should not be used as evidence that dual-runtime bootstrap has run.
